What Plainfile could grow into

A hypothetical, using only what the architecture already allows: a static web app over a folder of markdown files (local, or Dropbox and later OneDrive and Google Drive), no server of ours, no accounts, no database. Every screen below is a view computed from your files. Nothing here is built unless an earlier release says so.

What stays true, and what this cannot be

Within the architecture

  • Everything is a view over plain markdown and frontmatter. Delete the app and the files are fine.
  • Local folder, Dropbox (built), later OneDrive and Google Drive. Same screens on all.
  • Works offline with a saved index, installs as an app, syncs through the folder's own tool.
  • Custom views, templates and saved filters are small files in .plainfile/.
  • Safe writes, previews, Undo and a readout of every change.

Out of reach without a server

  • Real-time co-editing or shared comments (two people editing at once). Sharing happens through the shared folder, with conflicts surfaced.
  • Push notifications and reminders when the app is closed (a phone can show them only while it runs).
  • Email, Slack or calendar integrations that need a backend (read-only .ics import is possible).
  • Server-side search across devices, accounts and sign-in of our own.
  • AI features need your own API key typed into the browser, which I would not add by default.

If I had to order it

1 Phone pass and bottom tabs · 2 Saved index and Dropbox incremental sync (speed and offline) · 3 Home and the weekly review · 4 Calendar and People · 5 Export and status reports · 6 Insight views. Each is a separate release, and each can be dropped without hurting the rest.
